License Server API

Every channel between a client site and the license server — the LicenseBox-style pull API, the server→site license-push, and the admin panel's session API — with the trust model behind each.

9 site endpoints 1 push channel 21 admin routes HMAC-signed certs & tokens 503 maintenance + Retry-After Per-IP throttles

How the pieces talk architecture

Two directions, two guarantees: sites pull verdicts over HTTPS to a fixed host; the server only ever pushes a wake-up — never a verdict.

Failure codes status_code

Every status:false carries a stable machine code — this is how the plugin tells "product withdrawn" apart from "activation disabled".

CodeMeaning / site behavior
INVALID_API_KEYLB-API-KEY matches no product.
PRODUCT_DISABLEDProduct withdrawn → UI shows "This product is no longer available."
LICENSE_SUSPENDEDLicense suspended in admin.
LICENSE_INACTIVELicense not active (catch-all).
LICENSE_EXPIREDexpires_at in the past.
ACTIVATION_DISABLEDThis domain's activation row disabled → "enter a different code" flow.
DOMAIN_NOT_ACTIVATEDCert's bound domain ≠ request's LB-URL domain.
ACTIVATED_MAXIMUM_ALLOWED_PRODUCT_INSTANCESSeat limit reached.
SERVER_UNAVAILABLEHTTP 503 — planned maintenance, not a denial. Carries Retry-After; sites keep their last verdict and re-check on that schedule.
HTTP 429Per-IP failure throttle tripped.

Why a site can't be remotely killed threat model

Attack pathGuard
Forged verify_license responseHTTPS only; api_base allowlisted to *.ez-it-solutions.com client-side.
Forged license-pushPush carries no verdict — worst case is an extra verify. Throttled 15s/site.
deactivate_license Mode BNeeds license_code — lives inside the signed cert, never shipped.
Domain spoofing (LB-URL)Domain is bound into the cert at activation; verify rejects mismatches.
Cert forgery / replayHMAC server_secret|api_key; domain + product pinned inside.
Brute force (codes / passwords / admin)Per-IP failure throttles → 429; IP from TCP peer, never headers.
Maintenance read as denial503 + SERVER_UNAVAILABLE is classified planned maintenance — sites preserve their verdict instead of gating.
Recovery code lifted from a site DBSite stores only the digest; the raw code never leaves the server's Products panel.
Push as SSRFhttp(s)-only targets; redirects never followed, so keys can't be relayed.

Residual: api_key is distributed by design; the get_config doc is unsigned (client-side host allowlist is the boundary); admin throttle is per-IP.
